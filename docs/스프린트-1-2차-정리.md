# 1차·2차 스프린트 개발 정리

## 개요

| 스프린트 | 기간 | 포함 티켓 |
|---|---|---|
| 1차 | 2026-07-12 ~ 2026-07-27 | IH2-22 메뉴 구조 관리 |
| 2차 | 2026-07-27 ~ 2026-08-10 | IH2-19 공통코드 그룹 관리, IH2-20 공통코드 항목 관리, IH2-12 직원 정보 관리(등록/수정/조회), IH2-6 로그아웃, IH2-5 로그인 |

대상 저장소:
- FE: `hisfrontend` (Next.js App Router / TypeScript / Redux Toolkit + redux-saga)
- BE: `admin-service` (Spring Boot / Gradle / Oracle)

공통 아키텍처 원칙(모든 기능에 공통 적용):
- FE: `components/{service}`(화면) → `features/{service}/{api,saga,slice,types}`(상태/통신)로 계층 분리. 컴포넌트는 `dispatch(fetchXxxRequest())`만 하고, 실제 API 호출은 saga가 담당.
- BE: `{domain}/controller` → `service`(인터페이스+impl) → `repository`(JPA) → `entity`. 응답은 항상 `ApiResponse<T> { code, message, data }` 포맷.
- 에러 처리: `BusinessException(ErrorCode.XXX)`를 던지면 `GlobalExceptionHandler`가 가로채서 `{code: HTTP상태, message: 실제메시지}`로 변환. 이 패턴을 안 쓰고 `IllegalArgumentException` 등 일반 예외를 던지면 `GlobalExceptionHandler`의 catch-all(`Exception`) 핸들러로 떨어져 **HTTP 500 + 예외 클래스명 노출**로 새어나간다 — 이번 정리에서 반복적으로 등장하는 미비점.

## 1차 스프린트

### IH2-22 메뉴 구조 관리

**현재 상태: 실제로는 "메뉴 구조 관리(CRUD)" 기능이 아니라, 사이드바에 뿌릴 메뉴 트리를 읽기 전용으로 조회하는 기능만 구현되어 있다.** 메뉴 등록/수정/삭제 화면, API 전부 없음.

#### FE 구성

| 파일 | 역할 |
|---|---|
| `src/features/system/api/menuApi.ts` | `fetchMenuApi()` — `GET /api/menu` 호출 후 `ApiResponse.data`를 꺼내 `toMenuTree()`로 변환 |
| `src/features/system/saga/menuSaga.ts` | `fetchMenuRequest` 액션을 `takeLatest`로 감시 → API 호출 → `fetchMenuSuccess`/`fetchMenuFailure` |
| `src/features/system/slice/menuSlice.ts` | slice 이름은 `"menu"`. state: `{ items, loading, error }`. 액션은 `fetchMenuRequest/Success/Failure` 3개뿐 — 등록/수정/삭제 액션 자체가 없음 |
| `src/features/system/types/menuTypes.ts` | `MenuRow`(BE 엔티티와 1:1), `MenuTreeNode extends MenuRow { children }` |
| `src/features/system/util/menuTree.ts` | `toMenuTree(flatRows)` — flat 배열을 부모/자식 관계로 묶어 트리로 변환하는 순수 함수 (2-pass: id map 생성 후 parentMenuId로 연결) |
| `src/components/sidebar/Sidebar.tsx` | 유일한 소비처. `menuTree`/`loading`/`error`를 props로 받아 그리기만 하는 순수 표시 컴포넌트 |

**주의할 점(문서화 가치 있음)**: `menuSlice`는 내부적으로 `"menu"`라는 이름을 쓰지만, `rootReducer.ts`에는 `system: systemReducer`(menuSlice를 import)로 등록되어 있다. 그래서 Redux DevTools에서는 `state.menu`가 아니라 **`state.system.items`**로 보인다. 이름과 실제 마운트 키가 다르니 신규 합류자가 헷갈리기 쉬운 지점.

`AppShell.tsx`가 마운트 시 `dispatch(fetchMenuRequest())`를 1회 호출해서 로그인된 모든 사용자에게 동일한 메뉴 트리를 내려준다 — 사용자별/역할별 메뉴 필터링은 없다(이 부분은 로그인 섹션의 "권한/역할 모델 없음" 이슈와 동일 선상).

#### BE 구성

| 파일 | 역할 |
|---|---|
| `menu/controller/MenuController.java` | `GET /api/menu` 단 하나. `ApiResponse<List<MenuEntity>>` — DTO 계층 없이 엔티티를 그대로 응답에 실어 보냄(commonCode/emp와 다른 점) |
| `menu/service/MenuService.java`, `service/impl/MenuServiceImpl.java` | `selectMenuRows()` → `repository.findByUseYnOrderBySortOrderAsc("Y")` (비활성 메뉴는 관리자에게도 안 보임 — `useYn` 필터가 하드코딩) |
| `menu/repository/MenuRepository.java` | `JpaRepository<MenuEntity, Long>` + 커스텀 메서드 1개 |
| `menu/entity/MenuEntity.java` | `@Table(name = "MENU")` |

| PARENT_MENU_ID | parentMenuId | |
| MENU_CODE | menuCode | |

#### REST API

- `GET /api/menu` → `ApiResponse<List<MenuEntity>>` — 파라미터 없음. **이게 전부.**

#### 검증/예외 처리

해당 없음 — mutating 엔드포인트가 없어서 검증할 입력값 자체가 없다.

#### 미비점 / 후속 과제

- 메뉴 등록·수정·삭제 화면과 API가 통째로 없음 (IH2-22를 "관리" 기능으로 완성하려면 이 부분이 본작업)
- 사용자 역할/부서별 메뉴 필터링 없음 — 로그인한 모든 계정이 동일한 메뉴를 봄
- `admin/emp` 라우팅 이슈(2차 스프린트에서 실제로 겪음 — 아래 참고)처럼, `MENU` 테이블 데이터는 DB에 직접 들어있고 코드로 버전관리되지 않음. 나중에 메뉴 URL을 바꾸는 작업을 할 때 **DB UPDATE 후 반드시 COMMIT까지 해야** 반영된다(이번 스프린트 중 실제로 커밋 누락으로 인한 404를 겪었음 — 아래 IH2-5/6 섹션 참고).

## 2차 스프린트

### IH2-19 / IH2-20 공통코드 그룹·항목 관리

**현재 상태: 조회·등록·수정은 end-to-end로 완성되어 있음. 삭제 기능은 아예 없음(하드 삭제 API 자체가 없고, `useYn`을 `N`으로 바꾸는 비활성화가 사실상의 삭제 대체 수단).**

#### FE 화면 구조

- 진입점: `src/app/admin/commoncode/page.tsx` → `<CommonCodeGroupList />`
- `CommonCodeGroupList.tsx`: 좌측에 그룹 목록 테이블(키워드/사용여부 클라이언트 필터), 행 클릭 시 우측에 `<CommonCodeItemPanel>` 표시. "그룹 등록" 버튼 → `Modal` + `CommonCodeGroupRegisterForm`
- `CommonCodeGroupRegisterForm.tsx`: `fetchCommonCodeGroupRegisterRequest({ groupCode, groupName, useYn })` dispatch. 로그인/로그아웃 폼과 동일한 `waitClose` ref 패턴으로 성공 시에만 모달 닫음
- `CommonCodeGroupUpdateForm.tsx`: `groupCode`는 읽기 전용(식별키), `groupName`/`useYn`만 수정 가능
- `CommonCodeItemPanel.tsx`: 선택된 그룹의 항목 목록. "항목 등록"/행별 "수정" 버튼으로 각각 모달 오픈. "그룹 수정" 버튼도 여기 있음
- `CommonCodeItemRegisterForm.tsx` / `CommonCodeItemUpdateForm.tsx`: 항목 등록/수정. `codeValue`는 수정 시 읽기 전용

#### FE 상태 관리

**그룹**: `features/commonCode/api/commonCodeGroupApi.ts` (`GET /list`, `POST /register`, `PUT /update/{groupId}`) → `saga/commonCodeGroupSaga.ts`(`fetchCommonCodeGroupRequest/RegisterRequest/UpdateRequest` 감시) → `slice/commonCodeGroupSlice.ts`(state: `{ groups, loading, error }`, 등록 시 배열 끝에 push, 수정 시 `map()`으로 해당 `groupId` 교체)

**항목**: `features/commonCode/api/commonCodeItemApi.ts` (`GET /list?groupId=`, `POST /register`, `PUT /update/{codeId}`) → `saga/commonCodeItemSaga.ts` → `slice/commonCodeItemSlice.ts`(state: `{ items, loading, error }`)

**재사용 컴포넌트**: `features/commonCode/hooks/useCommonCodeOptions.ts` + `components/commonCode/CommonCodeSelect.tsx` — 그룹코드를 넘기면 해당 그룹의 활성(`useYn='Y'`) 항목들을 `{value, label}` 옵션으로 변환해주는 공통 드롭다운. 프리텍스트 입력 대신 강제해서 백엔드 공통코드 검증 실패를 원천 차단하려는 목적. **실사용처**: 검사/영상(`lab-imaging`) 서비스의 `LabOrderReceptionForm`, `ImageOrderReceptionForm`, `ImageScheduleRegisterForm` — 공통코드 그룹/항목 관리 화면 자체보다 오히려 다른 서비스에서 더 널리 쓰이는 인프라성 컴포넌트다.

참고: `fetchCommonCodeItemsByGroupCode(groupCode)`는 "그룹코드로 항목 조회" 전용 BE 엔드포인트가 없어서, 그룹 목록 API로 groupCode→groupId를 먼저 찾고 항목 API를 또 호출하는 **2회 왕복** 방식으로 구현되어 있다. 트래픽이 많아지면 개선 여지가 있는 지점.

#### BE 구성

- `commonCode/controller/CommonCodeGroupController.java`, `CommonCodeItemController.java`
- `service` / `service/impl`, `repository`, `entity`, `dto`, `mapper` — 그룹/항목 각각 대칭 구조

#### REST API

**그룹** (`/api/commonCodeGroup`)
- `GET /list` → `ApiResponse<List<CommonCodeGroupEntity>>`
- `POST /register` → body `{ groupCode, groupName, useYn }`
- `PUT /update/{groupId}` → body 중 `groupName`/`useYn`만 반영
- DELETE 없음

**항목** (`/api/commonCodeItem`)
- `GET /list?groupId=` → `ApiResponse<List<CommonCodeItemEntity>>`
- `POST /register` → body `{ groupId, codeValue, codeName, useYn }`
- `PUT /update/{codeId}` → body 중 `codeName`/`useYn`만 반영
- DELETE 없음

#### DB 테이블

**COMMON_CODE_GROUP** (PK: `GROUP_ID`, 시퀀스 `COMMON_CODE_GROUP_SEQ`)
| 컬럼 | 필드 |
|---|---|
| GROUP_ID | groupId |
| GROUP_CODE | groupCode |
| GROUP_NAME | groupName |
| USE_YN | useYn |

**COMMON_CODE** (PK: `CODE_ID`, 시퀀스 `COMMON_CODE_SEQ`)
| 컬럼 | 필드 | 비고 |
|---|---|---|
| CODE_ID | codeId | |
| GROUP_ID | groupId | |

| CODE_VALUE | codeValue | |
| CODE_NAME | codeName | |
| SORT_ORDER | sortOrder | **API로 설정 불가, 화면도 정렬에 안 씀(그냥 등록 순서/`codeId` 순) — 사실상 죽은 컬럼** |
| USE_YN | useYn | |

#### 검증/예외 처리 — 미비점

- `ErrorCode.java`에 공통코드 전용 코드가 **하나도 없음**
- `updateCommonCodeGroup`/`updateCommonCodeItem` 둘 다 `.orElseThrow(() -> new IllegalArgumentException("Invalid group ID"))` 패턴 — 로그인/직원 정보에서 고쳤던 것과 동일한 버그. `GlobalExceptionHandler`가 못 잡아서 **HTTP 500 + 예외 클래스명 노출**
- `CommonCodeGroupDto`/`CommonCodeItemDto`에 `@Valid`/`@NotBlank` 같은 Bean Validation이 전혀 없음 — 빈 `groupCode`/`codeValue`로 등록해도 서버가 그냥 받아준다 (화면에서만 `required`로 막고 있어 API 직접 호출 시 우회 가능)
- `groupCode`/`codeValue` 중복 방지 로직 없음(JPA 엔티티에 `unique` 제약도 안 보임 — DB DDL에 유니크 인덱스가 있는지는 엔티티 코드만으로는 확인 불가, 별도 확인 필요)

### IH2-12 직원 정보 관리(등록/수정/조회)

FE `src/components/emp/` + `src/features/emp/`, BE `emp` 패키지.

#### FE 화면

- `EmpList.tsx`: 목록 + 검색(사번/이름/부서명) + 재직상태 필터, 행 클릭 시 우측 상세 패널(`EmpDetailPanel.tsx`)
- `EmpRegisterForm.tsx`: 등록 폼. 이름/연락처/입사일/부서 **필수 검증 이미 있음**(인라인 에러)
- `EmpUpdateForm.tsx`: 수정 폼. **이번 2차 스프린트(IH2-50)에서 이름/연락처/부서 필수 검증을 새로 추가함** — 원래는 검증이 전혀 없었음

#### FE 상태 관리

`features/emp/api/empApi.ts` → `saga/empSaga.ts` → `slice/empSlice.ts`(state: `{ emps, selectedEmp, loading, error }`), 목록/등록/수정/상세 각각 Request/Success/Failure 액션 트리오.

#### BE 구성 (`EmpServiceImpl.java`)

- **등록(`createEmp`)**: 사번(`EMP_NO`)을 `E{YYYYMM}{3자리 순번}` 형태로 자동 채번. 월별로 리셋되는 값이라 동시 등록 시 충돌 가능 → `DataIntegrityViolationException`을 잡아서 **최대 5회 재시도**. 등록과 동시에 로그인 계정(`ACCOUNT`)도 자동 생성(`LOGIN_ID=EMP_NO`, 초기 비밀번호는 임시 고정값 `"1111"`, 이후 로그인 시 이 값으로 로그인 가능 — 실제 정책 확정 필요)
- **수정(`updateEmp`)/상세(`getEmpById`)**: 원래 `.orElseThrow(() -> new IllegalArgumentException("Invalid Emp ID"))`로 되어 있어서 **HTTP 500 + 클래스명 노출** 버그가 있었음. **이번 2차 스프린트에서 `BusinessException(ErrorCode.EMP_NOT_FOUND)`(HTTP 404, "직원 정보를 찾을 수 없습니다.")로 교체 완료.**
- **등록 자체의 서버측 필수값 검증은 아직 없음** — 화면(FE)에서만 막고 있고, BE `createEmp`는 빈 이름으로 호출해도 그대로 저장한다. 이번 스프린트에서 "화면에서 이미 막고 있으니 이번엔 범위 제외"로 명시적으로 결정, 후속 과제로 남김.

#### REST API

- `GET /api/emp/list`
- `POST /api/emp/register`
- `PUT /api/emp/update/{empId}`
- `GET /api/emp/detail/{empId}`

#### ErrorCode 추가분

| 코드 | HTTP | 메시지 | 용도 |
|---|---|---|---|
| ADM009 | 404 | 직원 정보를 찾을 수 없습니다. | `EMP_NOT_FOUND` — updateEmp/getEmpById 대상 미존재 |

#### 미비점 / 후속 과제

- `createEmp` 서버측 필수값 검증 없음(범위 제외로 결정됨, 필요 시 별도 진행)
- `failCount`(로그인 실패 횟수) 컬럼이 `ACCOUNT`에 있지만 어디서도 증가/사용되지 않음
- 초기 비밀번호가 고정값(`"1111"`)이고 평문 비교 — 비밀번호 해싱/변경 정책 미정

### IH2-6 로그아웃

하위: **IH2-61(로그아웃 처리)**, **IH2-60(세션/토큰 무효화)**, **IH2-59(클라이언트 상태 초기화)**. **IH2-62(로그아웃 후 접근 차단 및 재인증 유도)는 이번 스프린트 범위에서 제외**하고 로그인 쪽 IH2-58로 흡수됨(아래 참고).

#### IH2-61 로그아웃 처리

- `Sidebar.tsx` 하단에 "로그아웃" 버튼 추가. 클릭 시 공통 `ConfirmDialog`로 "정말 로그아웃하시겠습니까?" 확인
- 확인 시 `dispatch(fetchAuthLogoutRequest())` → 기존 `fetchAuthLogoutSaga`(`features/auth/saga/authSaga.ts`)가 `POST /api/auth/logout` 호출 → `localStorage.removeItem("userInfo")` → `fetchAuthLogoutSuccess`
- Sidebar에 `waitLogout` ref(로그인 폼의 `waitRedirect`와 동일 패턴) + `useEffect`로 성공/실패 감시: 성공 시 `router.replace("/login")`, 실패 시 하단에 `Alert`로 에러 메시지

#### IH2-60 세션 무효화 (BE)

- `AuthController.logout()`이 `session.invalidate()` 호출 — **이미 구현되어 있었음, 코드 변경 없이 curl로 검증만 진행**: 로그아웃 후 같은 세션 쿠키로 `/api/auth/me` 재호출 시 `400 로그인이 필요합니다.` 확인됨

#### IH2-59 클라이언트 상태 초기화 — **구현 후 되돌림(중요)**

처음에는 로그아웃 시 Redux 스토어 전체를 초기 상태로 리셋하는 기능을 만들었다(`rootReducer.ts`를 감싸서 로그아웃 성공 액션을 감지 → `appReducer(undefined, action)` 호출). 이후 두 가지 이유로 **전부 되돌리고 제거함**:

1. **의존 방향 문제**: `rootReducer.ts`(store 계층)가 `features/auth`의 특정 액션을 직접 import하는 구조가 됨 — store가 특정 feature를 알아야 하는 역방향 의존. `src/store/resetStoreAction.ts`라는 새 파일을 만들어 store 소유의 범용 액션으로 우회하는 방법도 시도했으나,
2. **"새 파일을 굳이 만들 필요 없다"는 판단**으로 이 접근 자체를 폐기. 최종적으로 `rootReducer.ts`는 리더 승인 없이 손대지 않는 원래 상태(순수 `combineReducers`)로 완전히 원상복구했고, `resetStoreAction.ts`도 삭제, `authSaga.ts`도 원래대로 `fetchAuthLogoutSuccess()`만 dispatch하도록 되돌림.

**현재 최종 동작**: 로그아웃하면 `auth` 슬라이스(로그인 사용자 정보)만 비워진다. 직원 목록/환자 목록 등 다른 화면에서 조회했던 Redux 데이터는 로그아웃해도 스토어에 남아있는다(단, `/login`으로 리다이렉트되면서 해당 컴포넌트들이 언마운트되고, 재로그인 후 다시 그 화면에 들어가면 각 컴포넌트가 마운트되며 새로 fetch하므로 화면상 문제는 거의 없음). 공용 PC에서 연속 로그인하는 극히 짧은 순간에 이전 사용자 데이터가 스칠 수 있는 정도의 리스크만 남아있고, 이는 감수하기로 결정함. **`rootReducer.ts`에 로그아웃 관련 리셋 로직을 재도입하지 말 것** — 다시 필요해지면 새 파일 생성 여부부터 다시 확인받을 것.

#### REST API

- `POST /api/auth/logout` → `ApiResponse<Void>`

### IH2-5 로그인

하위: **IH2-53(로그인 인증 처리)**, **IH2-55(로그인 성공 시 세션/토큰 발급)** — 이 둘은 이전 스프린트에서 이미 완료. 이번 2차 스프린트에서는 **IH2-54(로그인 입력값 검증 및 오류 처리)**, **IH2-58(권한 정보 로딩 및 초기 접근 제어, 범위를 "로그인 가드+사용자 정보 로딩"으로 축소)** 진행.

#### IH2-54 로그인 입력값 검증 및 오류 처리

**FE (`LoginForm.tsx`)**: 제출 시 아이디/비밀번호를 trim 후 빈 값이면 API 호출 없이 필드별 인라인 에러("아이디를 입력하세요." 등) 표시. 입력 시작하면 해당 필드 에러만 제거.

**BE (`AuthServiceImpl.login()`)**: 기존 검증 로직(빈값 → 계정조회 → 잠금 → 비밀번호비교 → 재직상태)의 조건/순서/메시지는 그대로 두고, `IllegalArgumentException` 4곳을 전부 `BusinessException`+`ErrorCode`로 교체:

| 코드 | HTTP | 메시지 | 대상 |
|---|---|---|---|
| ADM005 | 400 | 아이디와 비밀번호를 입력하세요. | 빈 값 |
| ADM006 | 401 | 아이디 또는 비밀번호가 올바르지 않습니다. | 계정 미존재/비밀번호 불일치/휴직 상태 — **3곳을 의도적으로 같은 코드로 통일**(계정 존재 여부가 새어나가지 않도록 하는 보안 목적, 기존부터 있던 설계를 그대로 유지) |
| ADM007 | 401 | 잠긴 계정입니다. 관리자에게 문의하세요. | `lockedAt != null` |
| ADM008 | 400 | 로그인이 필요합니다. | `/api/auth/me` 미인증 (아래 IH2-58 참고) |

**BE 버그 수정**: `GlobalExceptionHandler.handleBusiness()`가 `errorCode.getCode()`(코드 문자열, 예: "ADM006")를 응답 `message` 자리에 넣고 있던 걸 `errorCode.getMessage()`(실제 한글 메시지)로 수정. 이 버그 때문에 `BusinessException` 경로를 타는 모든 응답이 사용자에게 코드 문자열을 그대로 보여줄 뻔했음.

**추가 정리**: `AuthController.me()`가 유일하게 예외 방식을 안 쓰고 `ApiResponse.error(400, "로그인이 필요합니다.")`를 직접 리턴하던 것도 `BusinessException(ErrorCode.AUTH_LOGIN_REQUIRED)` 방식으로 통일. 그 결과 `ApiResponse` 클래스의 `error()` 정적 팩토리 메서드가 완전히 미사용이 되어 삭제함. 이 변경으로 `/api/auth/me`의 미인증 응답이 "HTTP 200 안에 code:400을 담은 형태"에서 **진짜 HTTP 400**으로 바뀌었는데, FE `axios` 인터셉터가 이미 HTTP 에러를 처리하는 구조라 FE 쪽 수정 없이도 정상 동작함을 curl로 확인.

**`failCount` 기반 계정 자동 잠금 로직은 이번 범위에서 제외**(컬럼은 있지만 사용 안 함, 후속 과제로 남김).

#### IH2-58 권한 정보 로딩 및 초기 접근 제어 (범위: 로그인 가드 + 사용자 정보 로딩)

원래 "권한 정보 로딩"이라는 이름 때문에 역할(role) 기반 권한 시스템을 새로 만드는 걸로 오해할 여지가 있었으나, 조사 결과 **이 프로젝트엔 역할/권한 개념 자체가 아예 없음**(DB에 role 컬럼 없음, BE에 Spring Security 필터체인 없음, `/api/menu`도 로그인 여부 무관하게 전체 공개)을 확인하고, 이번 스프린트에서는 **"로그인 가드(미인증 시 /login으로 이동) + 이미 있는 사용자 정보(AuthUser) 로딩"**으로 범위를 명시적으로 축소함. 역할 기반 메뉴 필터링, BE 인가(Security) 도입은 별도 후속 티켓으로 분리.

**구현 (`AppFrame.tsx`)**:
- `/login`이 아닌 경로 진입 시, 이미 만들어져 있었지만 아무도 호출하지 않던 `fetchAuthMeRequest()`(→ `GET /api/auth/me`)를 실제로 dispatch
- 3가지 렌더링 상태: **확인 중**(로딩 화면) → **인증됨**(`AppShell` 렌더) → **미인증**(`/login`으로 `router.replace`)
- 이미 로그인 직후라 `state.auth.user`가 있으면 재확인 없이 바로 통과 (중복 API 호출 방지)

**까다로웠던 부분 — `meChecked` ref 리셋**: "이미 확인했으면 재요청 안 함"을 위해 `useRef`로 플래그를 뒀는데, 이 플래그를 로그아웃 후에도 안 지우면 "로그아웃 → 다시 보호된 페이지 진입 → 이미 확인한 걸로 착각해서 재확인 안 함 → '확인 중...' 화면에 무한정 멈춤" 버그가 생긴다. 원인은 로그아웃으로 `auth` 상태가 초기값(`user: null, error: null`)으로 돌아가는데, 이 초기값이 "아직 한 번도 확인 안 한 상태"와 구분이 안 되기 때문. 해결: `/login` 경로로 돌아올 때마다 `meChecked.current`를 `false`로 리셋해서, 다음 보호된 경로 진입 시 다시 확인하도록 함.

#### `admin/user` → `admin/emp` 경로 정리 (부수 작업)

로그인 성공 후 리다이렉트 대상(`/admin/emp`)과 실제 DB 메뉴 URL(`/admin/user`)이 어긋나 있던 걸 발견 — `/admin/emp/page.tsx`는 원래 `/admin/user`로 리다이렉트만 하는 껍데기였고, 진짜 화면은 `/admin/user/page.tsx`에 있었음. 코드베이스 전반이 `emp`로 일관되게 불리는 것과 맞춰 **역할을 서로 교체**: `/admin/emp`가 진짜 화면(`EmpList` 렌더)이 되고 `/admin/user`는 완전히 삭제. DB `MENU` 테이블의 `ADM_USER` 행 `MENU_URL`도 `/admin/user` → `/admin/emp`로 수동 UPDATE.

이 과정에서 겪은 실수: SQL을 실행했지만 **COMMIT을 안 해서** 실제로는 반영이 안 됐던 적이 있음(Oracle은 기본적으로 자동커밋이 아님). `UPDATE` 문 실행 결과로 "1행 업데이트됨"이 떠도, 그건 그 SQL 세션 안에서의 얘기고 다른 연결(실행 중인 BE 서버)에는 `COMMIT;`을 별도로 실행해야 반영된다 — DB 데이터가 코드로 버전관리되지 않는 이 프로젝트 구조상 앞으로도 반복될 수 있는 함정.

#### REST API (auth)

- `POST /api/auth/login` → `ApiResponse<AuthDto>`
- `GET /api/auth/me` → `ApiResponse<AuthDto>` (미인증 시 404 아님, `ADM008` 400)
- `POST /api/auth/logout` → `ApiResponse<Void>`
